# GitHub App Project Learning

GitHub repository connection is separate from optional Supabase GitHub social
sign-in. An existing signed-in Trace learner authorizes a GitHub App, selects a
repository and ingests a pinned commit through a read-only backend adapter.
Repository analysis and AI explanations do not execute code or grade a learner.

The integration is opt-in and disabled by default. Owner configuration is still
required before live authorization can be accepted. Automated fixtures do not
establish real GitHub installation, repository access or Gemini acceptance; see
[the acceptance report](../reports/trace-ai-and-github-acceptance.md) for current
local, browser and live-service evidence.

## Owner configuration

Register an owner-controlled **GitHub App**. Its name/slug is chosen by its owner;
set `TRACE_GITHUB_APP_SLUG` to the actual registered slug. Configure:

- Homepage: `http://localhost:3000` for the local frontend.
- User authorization callback: exactly
  `http://localhost:3000/projects/github/callback`.
- Setup URL after installation: the same exact callback above.
- Keep **Request user authorization (OAuth) during installation** disabled.
  For a new installation, Trace receives the setup callback, then explicitly
  starts user authorization with its saved owner-bound state and redirect URI.
  For an existing installation, Connect GitHub App starts user authorization
  directly; it does not depend on a setup redirect or changing repositories.
- Repository permissions: **Contents: Read-only**, **Pull requests: Read-only**
  and mandatory **Metadata: Read-only**. No repository writes, administration,
  secrets, Actions, organization membership or account permissions.
- Install using **Only select repositories**. Trace rejects all-repository
  installations, another App's installation, suspension, writes and unexpected
  permission categories.
- Keep webhooks disabled for this implementation. No webhook endpoint or webhook
  secret is required. Trace revalidates current user and installation access at
  source reads and before source/answer release.

The local backend is `http://localhost:8000`; the frontend API base must point
there and backend CORS must allow the exact frontend origin. Use the same
hostname throughout the authorization flow. Deployment needs a separately
approved HTTPS frontend/callback and backend origin; a teammate's loopback
address is not shared hosting. Production rejects non-HTTPS App callbacks.

Configure these names in the **backend process environment or approved secret
manager**, using [the safe template](../../backend/github.env.example):

| Variable | Meaning |
| --- | --- |
| `TRACE_GITHUB_APP_MODE` | `disabled` until all private configuration is ready; explicitly set `enabled` to activate |
| `TRACE_GITHUB_APP_ID` | Numeric App ID; different from OAuth Client ID |
| `TRACE_GITHUB_APP_SLUG` | Actual GitHub App slug |
| `TRACE_GITHUB_APP_CLIENT_ID` | App's OAuth Client ID |
| `TRACE_GITHUB_APP_CLIENT_SECRET` | Private App OAuth Client Secret |
| `TRACE_GITHUB_APP_PRIVATE_KEY` | Private RSA PEM generated by the App owner through GitHub |
| `TRACE_GITHUB_APP_STATE_SIGNING_SECRET` | Independent random signing secret, at least 32 characters |
| `TRACE_GITHUB_APP_TOKEN_ENCRYPTION_KEY` | Independent stable Fernet key: URL-safe base64 encoding of 32 random bytes |
| `TRACE_GITHUB_APP_CALLBACK_URL` | Exact registered frontend callback above |

The template is not loaded automatically. Do not append these to the strict
ordinary `backend/.env`; do not put private keys, secrets or tokens in root
`.env.local`, `NEXT_PUBLIC_*`, source, Git, chat or terminal transcripts. Configure
secrets privately through a secret manager or masked input; load the RSA PEM
from an owner-controlled file. Keep the token encryption key stable and backed
up privately. Losing/changing it makes saved credentials require reconnect;
Trace never fabricates or automatically provisions an owner credential.

For local Windows acceptance, open PowerShell in the repository root. Load the
two stable application secrets from your private secret store; do not regenerate
them on each launch. The following prompts keep secret values out of command
history and terminal output:

```powershell
$env:TRACE_GITHUB_APP_ID = Read-Host 'GitHub numeric App ID'
$env:TRACE_GITHUB_APP_SLUG = Read-Host 'Registered App slug'
$env:TRACE_GITHUB_APP_CLIENT_ID = Read-Host 'GitHub App Client ID'
foreach ($setting in @(
  'TRACE_GITHUB_APP_CLIENT_SECRET',
  'TRACE_GITHUB_APP_STATE_SIGNING_SECRET',
  'TRACE_GITHUB_APP_TOKEN_ENCRYPTION_KEY'
)) {
  $maskedValue = Read-Host $setting -AsSecureString
  $privateValue = [System.Net.NetworkCredential]::new('', $maskedValue).Password
  [Environment]::SetEnvironmentVariable($setting, $privateValue, 'Process')
  Remove-Variable privateValue, maskedValue
}
$pemPath = Read-Host 'Private GitHub App PEM file path'
$env:TRACE_GITHUB_APP_PRIVATE_KEY = Get-Content -LiteralPath $pemPath -Raw
$env:TRACE_GITHUB_APP_CALLBACK_URL = 'http://localhost:3000/projects/github/callback'
$env:TRACE_GITHUB_APP_MODE = 'enabled'
./scripts/run-gemini-backend.ps1 -ConfirmFreeTierProject
```

Keep this terminal open while testing. Another terminal or an already-running
server does not inherit these process settings. Stop the earlier local backend
before starting this one on port 8000. This launcher still reads Gemini's key
privately from `backend/.env.gemini`; it does not print either provider's secrets.
For normal repeated startup, use the team's private secret manager rather than
saving a shell script containing literal values. The App owner supplies the
GitHub credentials; a password/secret manager can generate the state secret,
and the encryption secret must have the exact Fernet format in the table above.

Enable expiring GitHub user tokens. Trace accepts a shorter provider expiry and
caps its own authorization at eight hours, including when the upstream response
omits expiry. Refresh tokens are not persisted or used: expiration requires an
explicit authorization flow. No new GitHub SDK, paid service or deployment is
activated by these settings. GitHub documents user-token permissions as the
intersection of the user and App permissions. [GitHub user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)

## Connection and disconnect sequence

1. A signed-in learner opens `/projects` and chooses **Connect GitHub App**.
2. `POST /api/v1/projects/github/installations/start` returns installation and
   user-authorization URLs, signed owner-bound state and a ten-minute expiry.
   The nonce is persisted and can be consumed only once.
3. The browser stores pending flow metadata in session storage, then visits
   GitHub's user-authorization page. An existing installation and its selected
   repositories are preserved; reinstalling or saving installation settings is
   not required.
4. Only if the App is not installed, use the separate **Install GitHub App**
   action. Its fresh flow visits GitHub's installation page for permission and
   repository selection. The setup callback saves the returned installation ID
   as an untrusted selection hint, then begins explicit user authorization.
5. GitHub returns its one-use code and state. The callback strips the query and
   submits the protected complete request; pending browser state is cleared.
6. The backend consumes the nonce before exchange, identifies the GitHub user,
   and uses that user's token to enumerate `/user/installations`. It matches the
   configured App ID and requires exactly one installation when no setup hint
   was supplied. An explicit hint must also belong to this user-accessible set.
   Fresh App/installation, selected-repository and read-only permission checks
   and user-scoped repository access checks precede encrypted
   owner/installation/user-bound credential persistence.
7. The learner explicitly selects a currently authorized repository. Every
   source operation rechecks access. Source reads use fresh installation tokens
   narrowed to that one repository and read-only permissions. GitHub supports
   this narrowing when creating installation tokens. [Installation-token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)

The same Trace account must finish the flow. Failed, expired or replayed state
requires restarting; an installation ID alone never grants access. User
credentials remain encrypted at rest and are never returned to the frontend.
Installation tokens are not persisted. Saved authorization works across backend
restarts/workers when they share the database and the same private encryption
key; it is no longer limited to the old five-minute process-memory proof.

Discovery is bounded to four pages of 25 installations and must be complete and
consistent; partial or malformed results fail closed. No matching installation
returns 404; multiple matches without a selection return 409. No credential is
stored in either case. An explicit selection outside the user's discovered set
returns 403. There is no multiple-installation picker in this bounded change.
The shared HTTP error boundary sanitizes error codes by status, so the callback
does not claim a more specific cause than the response proves. A 409 can also
mean expired, used or invalid state; every retry starts a fresh flow. An OAuth
callback needs only `code` and `state`; URL-supplied installation IDs do not
override saved setup selections or backend access checks.

Disconnect is explicit, owner-only and idempotent. A repository disconnect
marks that connection inactive while retaining snapshots. An installation
disconnect also wipes its encrypted user credential and invalidates all its
source access. Authorization/connection revisions invalidate operations already
in flight, including late AI output and persistence. Reconnecting is an explicit
new authorization/selection action. This local disconnect does **not** uninstall
the GitHub App or revoke all of the user's GitHub grants. Those controls remain
in the owner's GitHub settings. Upstream revocation, deleted repositories,
suspension and removed access block subsequent source reads/releases.

Owned connection metadata remains listable after expiration/disconnect;
repository source content needs current authorization. Returned `authorized`
status means an unexpired saved credential, not a promise that GitHub access
cannot have changed. Permission checks still run for each source operation.

## HTTP contracts

All paths below start with `/api/v1/projects/github`. They require a signed-in
learner Bearer token and return `Cache-Control: no-store`. Writes additionally
require an allowed Origin and `X-Trace-Client: learning-web`; authenticated GETs
do not require those write headers. Guest cookies alone grant no App access.

| Method/path | Input | Output |
| --- | --- | --- |
| POST `/installations/start` | No body | `installation_url`, `authorization_url`, `state`, `expires_at` |
| POST `/installations/complete` | `{code,state,installation_id?}`; omit the ID to discover a unique existing installation | Installation ID, selected-repository mode, authorization expiry and status |
| GET `/installations` | None | Owned installation summaries; `authorized`, `reauthorization_required` or `disconnected` status |
| POST `/installations/{installation_id}/disconnect` | No body | Disconnected installation summary; no tokens |
| GET `/installations/{installation_id}/repositories` | None | Currently authorized `{repository_id,full_name,private}` choices |
| POST `/repositories` | `{installation_id,repository_id}` | Owned connection with `connected`/`disconnected` status |
| GET `/repositories` | None | Owned connection summaries |
| POST `/repositories/{id}/disconnect` | No body | Disconnected connection summary |
| POST `/repositories/{id}/ingest` | `{commit_sha}` | Canonical V2 `RepositoryKnowledgeSnapshot` with coverage and exact references |
| GET `/repositories/{id}/knowledge?commit_sha=...` | Exact SHA query | Saved V2 artifact after fresh access checks |
| POST `/repositories/{id}/ask` | `{commit_sha,question,history?}` | Grounded `ProjectQuestionAnswer` with exact quotations and server-computed lines |
| POST `/repositories/{id}/sync` | `{commit_sha}` | Existing V1 changed-file `ProjectSnapshot` |
| GET `/repositories/{id}/snapshot?commit_sha=...` | Exact SHA query | Existing V1 snapshot after fresh access checks |
| POST `/repositories/{id}/learning-path` | `{commit_sha}` | Ungraded V1 path/questions; `ready` only after persistence commits, with saved `id` and `generation` provenance |
| GET `/repositories/{id}/learning-path?commit_sha=...` | Exact SHA query | Latest saved V1 path after current ownership/access and source checks; 404 if none is available; never generates |

Use the generated types in `src/lib/api/schema.d.ts` and the
`githubProjectsApi` adapter. The current `/projects` journey uses V2 ingest and
ask. Commit SHA is exactly forty lowercase hexadecimal characters, not a branch,
URL or filesystem path. Questions are at most 2,000 characters; optional history
has at most four user/assistant messages of 1,600 characters each. Total question
payload is capped at 9,000 UTF-8 bytes. History remains untrusted context and is
not persisted as learner evidence.

```ts
import { githubProjectsApi } from "@/lib/api/github-projects";

const connection = await githubProjectsApi.connect(installationId, repositoryId);
const knowledge = await githubProjectsApi.ingest(connection.id, exactCommitSha);
const reopened = await githubProjectsApi.knowledge(connection.id, knowledge.commit_sha);
const answer = await githubProjectsApi.ask(connection.id, {
  commit_sha: reopened.commit_sha,
  question: "Teach me how authentication works in this project.",
  history: [],
});
// Render answer.status, limitations, sections and exact source citations.
await githubProjectsApi.disconnect(connection.id);
```

An answer status is `answered`, `insufficient_information` or `unavailable`.
Only answered results contain sections and actual AI/test-fixture provenance;
unsupported or failed results contain no fabricated answer. No relevant sources
causes abstention without a provider call. Invalid citations or malformed
provider output reject the whole answer. HTTP 200 with unavailable is not success.

Missing account is 401; forbidden origin/role 403; foreign/missing connection
404; stale authorization/replay 409; invalid input 422; admission or upstream
rate limiting 429; unavailable configuration/dependency 503; deadline 504.
Sanitized middleware errors may generalize details: do not match private upstream
error strings. Limits are ten calls per account/minute, one active per account
and two globally, plus ingress controls. There are no automatic OAuth/AI POST
retries. Follow GitHub's numeric pagination through the backend, not arbitrary
client-supplied pagination URLs. [GitHub installation APIs](https://docs.github.com/en/rest/apps/installations)

## Bounded V2 ingestion and grounding

The server inspects repository metadata and the file tree at the exact commit.
It selects safe frontend/backend code, API routes/schemas, models, migrations,
documentation and supported native agent logs. This is bounded analysis; the
receipt always says `complete_repository:false` and reports partial coverage.

| Bound | Current implementation |
| --- | --- |
| Selected accessible repositories | At most 100; four numeric pages of 25 |
| Directory-tree requests | At most 20; at most 2,000 entries inspected |
| Persisted catalog | At most 240 entries |
| Source blobs fetched | At most 18; 32 KiB per blob |
| Source references | At most 40; 1,800 characters per exact excerpt |
| Aggregate source budget | 48,000 UTF-8 bytes |
| Commit history | At most 30 entries; three pages of ten |
| Pinned commit changed files | At most 75 entries; three pages of 25 |
| Durable artifact | At most 96 KiB of serialized JSON |
| Question retrieval | At most twelve owned source references |

Coverage exposes tree/history/changed-file completeness flags, counts and
explicit omission/budget reasons. An exhausted deadline/budget yields an honest
partial receipt when safe sources exist, or an error when none do. Oversized,
non-UTF-8, binary, generated, unsupported or unsafe files are omitted; genuine
authentication/network/integrity failures abort instead of masquerading as
ordinary omissions. Earlier history entries carry their observed title/time;
only the selected pinned commit has its fetched changed-file list.

Secret-bearing paths, `.env` files, key material, credentials, `node_modules`,
build outputs, lockfiles, generated declarations/minified assets and symlinks
are excluded. Safe names such as token-validation source can still be inspected;
actual sensitive storage is excluded and the entire file is privacy-checked
before excerpts are selected. The blob API reads pinned blob hashes and does
not follow a source filename into a different secret file. No repository clone,
shell execution, arbitrary file/URL loader or repository write is performed.
Filters are defense in depth; only authorize repositories approved for this
processing, rather than treating filtering as a proof every file is non-sensitive.

Each source reference pins its digest, exact path and line range. Answers retrieve
only the owned stored bundle, balance relevant frontend/backend material and
instruct Gemini to explain observed relationships conditionally. Citation IDs
must exist in the selected bundle; quotations must occur exactly in those
sources. The server supplies citation paths and computes line numbers from the
exact quotations. Unknown paths/endpoints/filenames and model-written line
claims are rejected. These checks establish source membership and quotation
integrity, not a proof of every natural-language inference. Missing routes,
external token creation and omitted relationships must remain unknown.

The only dot-directory exception is `.claude-logs/*.md`. Native counted
PROMPT/RESPONSE bodies may include validated entry number, session/turn/model
metadata and timezone-qualified timestamps when actually present. Frontmatter,
local paths, hidden reasoning, tools, uncounted tails, unsafe bodies and unknown
formats are withheld. Missing metadata stays missing. Correlation is explicitly
`same_pinned_snapshot_only`; prompt-to-file relationships remain `unproven`.
A log claim never establishes execution, learner competence or an exact commit
caused by a particular prompt.

V1 `/sync`, `/snapshot` and `/learning-path` remain separate from canonical V2.
The snapshot schema and historical digest rules are unchanged; current excluded
source paths are refused on release. V1 reads at most twelve changed files,
1,000-character excerpts and five associated PR titles. V2 does not claim a
complete PR discussion/diff archive. V2 question answers remain ephemeral.
V1 learning paths are saved privately with their explanations, questions and
reference IDs, bound to the owned connection, exact commit and snapshot digest.
Each saved response has an `id` and `generation` metadata: `provider_id`,
`requested_model_id`, optional `returned_model_id`, and `generated_at`.
No credential is part of that response or generation metadata. These are ungraded
explanations, not course completion or mastery records. Broad-topic private guides
retain their distinct owner-scoped persistence.

After selecting the repository and reading the exact commit, use **Load saved
learning path** to retrieve the latest saved result without a generation request.
The UI shows **Saved privately** only after a successful receipt with matching
commit, snapshot and citations arrives. A failed or uncertain generation response
does not imply a save failed: load the saved result before considering another
generation. Loading does not automatically generate or retry. Existing paths that
were displayed before persistence was implemented cannot be recovered from the
database; no historical generated content or provenance is fabricated.

Migration `0012_github_authorization` adds encrypted grants/revisioned disconnects;
`0013_repository_knowledge` adds immutable V2 artifacts alongside V1 history.
After the merged `0014` history, `0015_project_learning_paths` adds immutable saved
V1 learning paths. Its downgrade refuses to remove populated path history.
Back up each machine's own database, run the existing forward-upgrade procedure
and verify integrity before starting the new backend. These migrations are
additive; populated downgrade refuses to discard the new history. Never reset
an older database or copy another learner's database to obtain the schema.
See the acceptance report for actual local upgrade evidence; migration files
alone do not establish a production or hosted PostgreSQL upgrade.

## Manual acceptance after owner setup

1. Privately configure the App and stable encryption key, then start the backend
   with GitHub enabled and the separately approved free-tier Gemini launcher.
2. Sign in privately, install on a small approved repository containing frontend
   auth, a backend route/schema, a migration and a native counted agent log.
3. Complete both authorization callbacks and select that repository. Ingest an
   exact commit and inspect metadata, catalog, coverage and source lines against
   GitHub at that same SHA. Large/excluded files must be explicitly omitted.
4. Ask how authentication works; inspect frontend/backend explanation, exact
   quotes and computed line references. Ask a follow-up and an unsupported
   question; missing implementation must produce uncertainty, not an invented flow.
5. Reopen the saved artifact after a backend restart, using the same private
   encryption key. Expired authorization must require reconnect; it must not
   silently switch to App-only access.
6. Repeat with another Trace account, then disconnect locally and revoke access
   in GitHub settings. Foreign and revoked source/answer release must fail while
   historical records remain preserved.
7. Exercise cancellation, tampered/replayed state, missing configuration,
   rate limits and provider errors. Mark live acceptance only after this real
   authorization/repository/Gemini round trip succeeds. Browser fixture success
   is separate evidence, not a substitute for it.
